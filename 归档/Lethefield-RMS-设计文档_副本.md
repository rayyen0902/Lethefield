## 0. 项目背景

Lethefield 是一个由遗忘函数（Forgetting Function, FF）驱动的记忆状态场（Memory State Field），命名取自希腊神话忘川 Lethe + field，强调"遗忘"是驱动记忆场演化的生成机制，而非记忆的被动衰减附加项。

**部署策略**：核心团队自部署小规模集群，仅用于用户体验与测试；生产环境由第三方云服务商（阿里云、百度云、腾讯云等）部署运维（v0.13 更新，见 §0.5.2；混合本地+云端架构留作后续升级路径）。

## 0.5 价值观公理与商业模式（v0.13 新增，全文最高优先级）

> **地位说明**：本节是全文最高优先级约束，先于一切技术选型。后续所有架构决策凡与本节冲突者，需回到本节重新评审。§14 记忆可携带性是本节的直接推论之一。

### 0.5.1 价值观公理

1. **记忆是用户的核心资产，神圣不可侵犯**——如同现实世界中公民的自由。平台对记忆只有保管义务，没有任何使用权利
2. **AGI 时代，记忆本身是昂贵的，将来可能比算力更昂贵**——成本优化不得以记忆安全为代价；"多花算力保护记忆"是应付的保费，不是浪费
3. **威胁不可以来自我们**——"我们"指**开发者（架构 + 代码）**：架构不安全、代码有漏洞导致的越界与泄漏，都是我们的责任。安全必须建立在**结构性保证**上（架构上不可能越界），而非程序性保证（依赖我们的代码不出错）。"系统看起来在正常运行"不构成安全证据（与 §7.5.1 Dead Man's Switch 同源）。运维方行为不在本条范围（见 §0.5.2 运维方信任模型）
4. **我们提供的是记忆服务，不是 C 端产品**——C 端自身的安全（客户端防护、凭证保管等）是 C 端产品的责任域，不是我们的；我们的责任域是服务边界之内：**任何租户、我们自身、以及运维方，都无法触及其他租户的记忆**。C 端不安全不是我们可以不安全的借口
5. **纯技术讨论文化**——对同一问题在不同立场上有不同看法时，充分表达前提与论据、理性理解，而非对抗

**核心使命**：破除互联网封建主义——让用户自由选择产品与服务商，自由市场经济为用户的权力保驾护航。多家授权服务商并存、用户可自由迁移，市场竞争是约束各方行为的第一机制；记忆可携带性（§14）是这一使命的技术基石——用户走得掉，市场才管得住。

### 0.5.2 开发与部署形态

> **边界说明**：组织治理与商业模式（理事会/基金会/信托等法律结构、授权与收益分配）由独立的组织宪章规定，**不属于本文档范围**——宪章管组织，本文档管项目，两者独立演进。此处只记录对架构有直接推论的事实。

- **开发形态**：社区开源协作；核心团队负责科研、技术实现与工程可行性论证，产出技术革新与修复优化（由社区成员实施）
- **部署形态**：核心团队自部署小规模集群，仅用于用户体验与测试；生产环境由第三方云服务商（阿里云、百度云、腾讯云等）部署运维

**对架构的直接推论**：

1. **运维方信任模型：法律 + 市场，而非架构性不信任**——服务商员工偷看用户记忆，是服务商与其自己客户之间的法律责任问题，由服务商承担，不由本架构兜底；授权服务商不止一家、用户可自由迁移（§14），市场竞争是约束运维方行为的第一机制。因此 **per-space 加密不是公理级要求**——它可以作为服务商差异化竞争的可选产品特性，不进入核心架构
2. **架构必须可被第三方独立、正确地部署运维**——部署复杂度不再只是内部成本，而是服务商能否不出错地执行的可靠性问题
3. **自有小规模集群仅用于体验与测试**——与 §7.1 单节点起步一致；逻辑隔离方案（§7.4）在该规模下完全适用，维持为当前阶段实施方案
4. **目标架构重估（关键变更）**：在公理 2/3 与服务商运维形态下，per-space 物理隔离的定位从"成本不划算的过度工程"（v0.12 评估框架）转变为**价值观公理的直接推论 + 待论证工程可行性的目标架构**。此前的工程性质疑（per-request 冷启动延迟、Cassandra/ES 集群池调度、单集群 keyspace/index 上限）不再是否决理由，而是本项目科研议程的一部分（见 §10 待决问题）；外部方案原文与 v0.12 评估（见同目录存档文件）作为论证输入之一。**在工程可行性论证通过前，§7.4 逻辑隔离定案继续作为实施方案执行，本节不构成对它的即时推翻**

## 2. FF（遗忘函数）机制回顾

### 2.1 核心公式

```
FF(m, t, n, s) = s × e^(−λ × n × log(1 + t/t₀))
```

驱动衰减的主变量是**事件距离 n**，而非墙钟时间 t——衰减节奏与真实信息更替绑定，而非物理时间。

### 2.2 参数分层

- **Memory-object runtime**：每条记忆自身的运行时状态（当前 s 值、上次触发时间）
- **Agent-level constants**：λ，衰减率，按 agent 域在构建期固定
- **Query-time controls**：检索时动态参数 ρ，θ_effective = θ_base / ρ

### 2.3 显著性动态更新（δ）

- **+0.2** 强化：记忆被再次触发/引用
- **−0.5** 冲突失效：新信息与旧记忆冲突（主动纠错，非被动淡忘）
- **−0.1** 忽视惩罚：长期未被触及

### 2.4 遗忘视界（forgetting horizon）

```
n* = ln(s/θ) / (λ × ln(1+t/t₀))
```

预测某条记忆在阈值 θ 之下还能存活多少个事件距离，支持主动存储管理（提前归档/固化）。

## 3. 与 MAGMA / HAGE 的关系（原文核实版）

> 说明：以下内容基于对 MAGMA（arXiv:2601.03236，Jiang et al., UT Dallas, 2026年1月）与 HAGE（arXiv:2605.09942，同一团队，2026年5月）原文的直接核实，非二手转述。HAGE 是 MAGMA 的后续迭代，非完全并列的独立流派。

### 3.1 MAGMA 贡献
- 提出四正交关系图：语义 / 时序 / 因果 / 实体
- 节点四元组：`n_i = ⟨c_i, τ_i, v_i, A_i⟩`
- 策略引导式图遍历检索（Adaptive Traversal Policy），消融显示是最大单一贡献来源（去掉后 Judge 分从 0.700 降至 0.637）
- 双流记忆演化：快路径（同步、无 LLM 调用）+ 慢路径（异步、LLM 推断因果/实体边）
- **无任何遗忘/衰减/剪枝机制**——图只增不减

### 3.2 HAGE 贡献（在 MAGMA 基础上）
- 边从静态类型升级为可训练特征向量 `e_ij ∈ R⁴`
- 查询条件式加权遍历：`S(n_j|n_i,q) = λcos(v_j,q) + (1-λ)w_ij(q)`
- 强化学习联合优化路由网络与边表征（policy gradient + anchor regularization 防止漂移）
- LoCoMo 总分较 MAGMA 提升（0.700 → 0.739），代价是推理延迟/token 成本小幅上升
- **同样无任何遗忘/衰减机制**；论文中 Algorithm 1 出现的 γ 衰减项是单次检索内的路径分数衰减，与跨查询/跨时间的记忆状态衰减无关，不能与 FF 混淆
- 论文 Ethical Considerations 部分明确指出：持久记忆系统存在隐私风险，未内置任何隐私/保留策略机制

### 3.3 结论

FF 所解决的"记忆状态随时间/事件演化"问题，是 MAGMA 与 HAGE 均未覆盖的真实空白，Lethefield 的 FS/FF 并非重复造轮子。

## 4. RMS 图 Schema 设计

### 4.1 节点（Event-Node）

```
n_i = ⟨ c_i, τ_i, v_i, A_i, φ_i, ref_ex ⟩
```

| 字段 | 说明 |
|---|---|
| c_i | 事件内容 |
| τ_i | 时间戳 |
| v_i | 稠密向量（供语义图使用）。**v0.5 变更**：物理存储于 Elasticsearch 的 `dense_vector` 字段，与该节点的全文/属性字段同索引存放，按 `space_id` 隔离索引，不再单独维护向量数据库（见 §7） |
| A_i | 结构化属性（实体引用等） |
| ref_ex | 指回 EX 的原始事件 ID，保证任何时候可追溯到不可变原始记录。**该字段是 RMS 与 EX 之间唯一的关联机制——两者是逻辑引用关系，不做物理共存（见 §7.2）** |
| **φ_i**（FF 状态块，MAGMA/HAGE 均无） | 见下 |

**φ_i 字段明细：**

| 字段 | 说明 |
|---|---|
| s | 基准显著性（仅 δ 调整会写回该字段；FF 的指数衰减部分不物化，`s_effective` 一律在读取时现算，见 §13.1） |
| n_created | 创建时的事件序号 |
| n_last_touched | 最近一次被强化/引用时的事件序号（FF 事件距离 n 的计算基准） |
| n_star_cached | 缓存的遗忘视界预测值，后台定期刷新，避免每次查询重算 |
| reinforce_count / conflict_count | 累积 δ 调整次数，用于审计和调参 |

### 4.2 四类关系图（沿用 MAGMA/HAGE 划分）

- **时序图**：严格按时间戳排序，immutable，不参与任何衰减/剪枝
- **语义图**：cos(v_i,v_j) > 阈值时连接
- **因果图**：S(n_j|n_i,q) > δ 时建立，consolidation 阶段推断
- **实体图**：事件连接到抽象实体节点，解决对象永续性问题

**纠错关系（supersedes，v0.10 新增）**：归属因果图的一种特殊边类型 `n_new --supersedes--> n_old`，表达"新事件取代旧事件"这一事实。它记录的是取代关系本身（含发生时间），不包含"旧事件是错的"这类判断——判断由查询时策略处理（见 §5、§13.7）。supersedes 链（A 被 B 取代、B 又被 C 取代）天然支持，纠错被再次纠错时无需回写历史。

### 4.3 遗忘粒度：方案 A（当前采用）

**决策**：FF 衰减仅作用于节点层面，边不单独维护衰减状态。

- 四类边保持存在性判定（静态规则或未来可选的 HAGE 式可训练权重），只负责"连接存不存在/强度多少"
- 节点 `s` 衰减到阈值以下时，检索时被跳过，其所有边在遍历中自然失效
- 与现有 δ 更新机制（+0.2/−0.5/−0.1）天然对齐，因为 δ 本身定义在"记忆"单位上而非"关系"上

**已知局限 / 未来升级路径（方案 B）**：
- 面向 To C 场景当前方案 A 足够；To B / 工程用户场景可能需要更细粒度的按边衰减（尤其因果边的单独可信度追踪）
- 方案 B：每条边携带独立 φ_ij（s, n_last_touched 等），衰减率 λ 按四类图分别设定——建议时序边永不衰减（immutable ground truth）、语义边衰减最快、因果边衰减最慢（消融实验证明价值最高）、实体边接近不衰减
- 升级触发条件：出现明确的 To B 需求后再评估，不在当前版本中实现

### 4.4 图数据库落地方式

`s`、`n_last_touched` 等作为节点实时属性存储，查询时直接按属性过滤（`WHERE s > θ_effective`），不需要额外外部状态表。后台 consolidation worker（对应 MAGMA slow path）在做实体/因果推断的同时，顺带刷新到期的 `n_star_cached`。

**v0.5 定案**：底层图数据库为 **JanusGraph + Cassandra**（存储后端）+ **Elasticsearch**（mixed index 索引后端，同时承担全文/范围检索与向量检索，见 §7），单节点部署起步，后续通过 Cassandra/Elasticsearch 各自加节点实现水平扩展，不更换技术栈。

## 5. 查询侧 FF 接入 MAGMA 式检索（v0.1 暂定方案，待效果验证后调整）

FF 的 `s`（记忆鲜活度）与 MAGMA 的检索分数（查询相关性）是正交维度，不做简单相加，按检索四阶段分别处理：

- **Stage 2（锚点识别）**：RRF 融合照常产出候选锚点集，**不将 `s` 塞入 RRF**；候选集产出后做一次后置硬过滤，对候选节点现算 `s_effective`，低于 `θ_effective` 的丢弃。**v0.5 变更**：本阶段的语义相似度检索与关键词/属性检索均由 Elasticsearch 承担（前者走 `dense_vector` + kNN，后者走原生全文/范围查询），二者天然同源、同索引，RRF 融合逻辑不变
- **Stage 3（自适应遍历）**：转移分数扩展为 `S(n_j|n_i,q) = exp(λ1·φ(...) + λ2·sim(...) + λ3·log(s_effective(n_j)))`，用软惩罚而非硬过滤，避免结构关键但 s 值偏低的"桥节点"被过早排除；束搜索收敛后对最终候选池再做一次 `θ_effective` 硬过滤。本阶段完全由 JanusGraph（经 Cassandra）执行图遍历，不再访问 Elasticsearch
- **supersedes 处理（v0.10 新增）**：Stage 3 遍历中遇到带 `supersedes` 入边的节点（即已被取代的节点），默认沿边重定向至取代者继续遍历；被取代节点本身不进入最终候选池，除非查询显式要求追溯历史（如"当时认为的是什么"类问题）。被取代节点保留在图中、仍参与衰减与归档，不因被取代而删除——supersedes 只影响检索策略，不改变 §13.4 生命周期
- **Stage 4（叙事合成/token预算）**：在 MAGMA 原有 Salience-Based Token Budgeting 基础上叠加 `s_effective` 作为第二权重，两项分数都高的节点保留完整细节，查询相关但 s_effective 低的节点优先压缩为简短提示
- **`n_star_cached` 定位**：不参与实时计算，用于图数据库查询前置粗筛（`WHERE n_star_cached > $n_now`），把明显跨越遗忘视界的节点排除在候选宇宙之外，降低后续现算 `s_effective` 的开销
- **ρ 旋钮作用范围**：`θ_effective = θ_base / ρ` 仅作用于 Stage 2 与 Stage 3 收敛后的两处硬过滤，不影响 Stage 3 遍历中的软惩罚权重 λ3，保持"记忆鲜活度阈值"与"相关性权重"两个旋钮互不干扰

**v0.1 暂定参数取舍（后续按实测效果调整）**：
1. λ3 作为域常数（agent-level constant），不随查询意图动态调整（不同于 λ1/λ2 的按意图加权）
2. Stage 2 与 Stage 3 收敛后各做一次独立硬过滤，不合并为一次

**召回单元的本质澄清**：检索最终返回给上层的，始终是 Stage 3 自适应遍历产出的**带边子图**，而非孤立节点列表——这是图数据库相对纯向量检索的核心价值所在（能把"点"带出"面"：时序/语义/因果/实体关系一并呈现）。向量检索（Stage 2 一路信号）只贡献候选锚点，从不单独构成最终召回结果，因此"召回物"在架构上必然来自图数据库。

## 6. 明确排除范围（Out of Scope）

### 6.1 MS 延期至 2/3 期（1.0 不做）

**决策**：MS 在 1.0 版本中不开发，整体延后到 2/3 期视需要再启动（见 §1 延期决策说明）。

**此前讨论存档，供 2/3 期重启时参考起点（非 1.0 定稿内容）**：

- 目标产物边界：收敛在"重点事件 / 沉淀笔记"层次（RMS 子图聚合 + 线性化叙事），不做"技能包"（技能包属于 ES 范畴，同样已挂起）
- 笔记字段草案：`note_id / title / created_at / updated_at / source_node_ids（可空）/ tags / links / 正文`，不设 `origin`、`sync_status` 等实时同步状态机字段
- 同步节奏草案：从"实时推送"改为"周期性固化"——满足 `reinforce_count` 累计阈值且期间无 conflict，或用户主动触发"整理成笔记"
- 已否决的机制：MS 编辑反哺 RMS 的 δ 强化写回路径（不做，避免笔记本行为影响记忆系统状态）

### 6.2 Skill 不属于 Lethefield

**决策**：Lethefield 不存储、不生成、不管理任何形式的 Skill（Agent IDE 中的技能/技能包）。

**判断依据**：
- Skill 本质上不是记忆——它是一种确定性的、可执行的过程性资产，不该随时间衰减或模糊，只应显式迭代/弃用，与 FF 语义（事件重要性随事件距离衰减）根本冲突，强行纳入会破坏 RMS/FS 已有的一致性
- Skill 更接近"当前 LLM / Agent IDE 能力不够完善时，针对特定场景打的补丁"，其生命周期与模型能力曲线绑定，而非与用户的记忆/身份绑定；参考提示词工程的历史——早期大量针对模型局限的手工技巧（如显式要求分步思考），随着模型能力提升逐渐失效或被内化，不再需要专门维护。Skill 存在同样被模型迭代淘汰的风险，不适合作为 Lethefield 这类以持久记忆为核心资产的基础设施长期背负的模块
- Skill 已有成熟生态位（Agent IDE 的 Skill 机制），RMS 沉淀出的行为模式/重复因果链路数据可以通过 API 暴露给外部 Agent IDE 使用，由其自行生成/管理 Skill；Lethefield 不参与 Skill 的存储或生命周期管理

## 7. 技术栈选型（v0.5 定案）

> **v0.5 重大变更**：图数据库与向量检索选型定案，取代 v0.3（Memgraph）与 v0.4（Neo4j/ArangoDB 1.0 + JanusGraph 2.0 两阶段方案）中的历史判断。定案结果：**JanusGraph + Cassandra + Elasticsearch，单节点起步，1.0→2.0 是同一套系统的水平扩容，不涉及技术栈迁移；不引入 Milvus，向量检索改由 Elasticsearch 原生能力承担**。

### 7.1 图数据库选型定案：JanusGraph + Cassandra + Elasticsearch

**决策依据（按排除法）**：

| 候选 | 排除/保留理由 |
|---|---|
| Memgraph | 要求整图常驻内存，多租户云服务场景下内存成本随图规模无限增长不可持续，排除（v0.4 已定） |
| ArangoDB | **2023 年 10 月起许可证由 Apache 2.0 改为 Business Source License（BUSL 1.1），不再是 OSI 认可的开源许可证**；社区版二进制包另受"ArangoDB Community License"约束，**单集群 100GB 数据量上限 + 商业用途受限**——按团队规模测算，1.0 中后期即可能触及该上限，排除 |
| Neo4j | Community Edition 走 GPLv3，核心图引擎开源，但**集群/高可用能力锁定 Enterprise 闭源商业版**——"开源带来的长期扩展灵活性"在最需要扩展的维度（水平扩展）上恰恰缺失，排除 |
| NebulaGraph | Apache 2.0 完全开源，社区版本身即具备分布式能力，是一个可行选项；但相较 JanusGraph，其存储与图引擎一体化（自研架构），可插拔性、底层存储可替换性不如 JanusGraph（Cassandra/HBase 可选、可换），**综合考虑团队对"开源+可定制化开发的长期灵活性"的明确优先级，未采纳，但作为候选记录在案** |
| **JanusGraph** | **采纳**。Apache 2.0 完全开源，无任何功能锁在闭源版本；存储后端（Cassandra/HBase）与索引后端（Elasticsearch/Solr）均可插拔替换，定制化自由度最高；配合 Cassandra（而非 BerkeleyDB）作为存储后端，**单节点部署与后期集群扩容是同一套系统的自然生长，不需要更换存储引擎**，因此不存在 v0.4 版本原先担忧的"1.0→2.0 技术栈迁移成本" |

**存储后端选型的关键约束**：JanusGraph 必须搭配 **Cassandra**（而非 BerkeleyDB）作为存储后端才能保证"单机部署、后期扩展"这条路径成立——BerkeleyDB 是嵌入式单机存储引擎，没有分布式路径，若 1.0 图省事选用 BerkeleyDB，后期扩展时仍需整体更换存储后端，等于重新引入迁移成本。因此 **1.0 起步即用单节点 Cassandra + 单节点 Elasticsearch**，而非用更简化的嵌入式方案替代。

### 7.2 放弃 Milvus：向量检索改由 Elasticsearch 承担

**决策**：不引入 Milvus 或任何独立向量数据库。向量检索能力由 Elasticsearch 原生的 `dense_vector` 字段类型 + kNN（HNSW 索引）承担，与 JanusGraph mixed index 所用的 Elasticsearch 集群共用（详见 §7.3 关于图索引与日志聚合是否需要物理隔离的既有原则，向量检索与图索引因同属"支撑图检索"的用途，可共用同一 Elasticsearch 集群，不再单独物理隔离）。

**决策依据**：

1. **趋势判断**：向量检索能力正在从"独立数据库品类"降级为"任意数据库均可支持的数据类型"——PostgreSQL（pgvector/pgvectorscale）、MongoDB（Atlas Vector Search）、Oracle（23ai）等主流数据库均已内建原生向量支持；Elasticsearch 自 7.3 起支持 `dense_vector` 存储，8.0 起提供原生 kNN 检索。为"向量检索"单独引入一套专门系统，越来越是一个默认不必要的架构决策，除非有明确的规模理由
2. **数据分片形状与 Milvus 设计目标不匹配（核心理由）**：Milvus 类专门向量数据库的核心价值，是解决"单一全局命名空间下、十亿级向量的分布式近似最近邻检索"问题，其分片、路由、索引优化均为此设计。而 Lethefield 的检索模型按 §8 记忆空间隔离原则，**检索永远限定在单一 `space_id` 内，不存在跨空间的全局向量检索场景**。这意味着实际负载不是"一个超大全局索引"，而是"成千上万个互相独立、规模远小的小索引各自检索"——这是 Milvus 分布式能力完全用不上的负载形状
3. **规模测算**：按 1000 用户量级估算（年增约 1825 万 RMS 节点），若按"一个记忆空间≈一个用户"估算，单空间年增向量数量级约 1.8 万，远低于 pgvector 等单机方案开始出现性能瓶颈的量级（约 1000–2000 万向量），更不需要为此引入专为十亿级设计的分布式向量引擎
4. **组件成本**：放弃 Milvus 同时省去其分布式部署所需的 etcd、对象存储（MinIO/S3）、消息队列（Pulsar）等一整套子依赖，是本次技术栈精简中降低固定运维成本最直接的一步

**待观察项（非当前决策依据，仅记录）**：若未来出现单个记忆空间数据量远超其他空间、导致该空间在 Elasticsearch 单索引下检索延迟明显劣化的情况，优先方案是给该空间**单独扩容/加分片**（依赖 §7.4 的 `space_id` 分片策略），而非引入全局向量数据库。

### 7.3 EX 与 RMS 存储隔离原则（沿用 v0.4 判断）

**v0.6 定案**：EX 存储采用 **Cassandra**，与 JanusGraph 所用的 Cassandra，**必须是两个独立实例/集群，不可共用**。

**依据**：
1. JanusGraph 对 Cassandra 的使用是私有序列化格式，非通用表结构，与 EX 业务表结构直接共存会产生数据布局冲突
2. 访问模式不同——EX 是持续高频追加写，JanusGraph 图存储是读写混合，混用会产生资源争抢与延迟传导
3. 故障域与扩容节奏需独立——EX 作为不可变 source of truth，其可用性不应受图查询负载波动影响

**关联机制**：EX 与 RMS 之间不做物理共存，仅通过 §4.1 已定义的 `ref_ex` 字段做逻辑引用。

**已知权衡（拍板时留痕）**：EX 主要访问模式是持续追加写、查询频率低，符合 Cassandra 适用场景；但审计与"Agent 建议 vs 人类最终决策"对比分析这两类低频读取场景需要灵活的临时性查询条件，是 Cassandra 相对 PostgreSQL 的已知短板，且迁移决策发生在实际写入量、查询模式尚未通过真实流量验证之前。团队已知晓上述权衡，选择直接定案，不再等待实测数据。

### 7.4 space_id 分片策略（v0.8 定案）

**已确认**：所有检索（Stage 2 的 Elasticsearch 检索，Stage 3 的 JanusGraph 遍历）均在单一 `space_id` 内完成，不存在跨空间检索场景。这天然规避了分布式图数据库最大的痛点——多跳遍历跨分片导致的网络往返开销。

**v0.8 定案**：

- **Cassandra**：`space_id` 作为分区键（标准做法）。Cassandra 靠一致性哈希将不同分区键值自动分散到集群各节点，这是其内建分发机制，不需要额外的"物理分片"决策。不做 per-space 独立 keyspace 或独立集群。
- **Elasticsearch**：共享 index + `space_id` 做 **custom routing**，不做"每个 space 一个 index"。指定 routing 值后，同一 space 的所有文档（含向量字段）会被强制路由到同一分片，查询时带上 routing 值直接命中该分片，效果上等同于对该 space 单独建了一个索引，但不需要管理成千上万个独立 index（index 数量暴涨会拖累集群 cluster state 同步开销，是 ES 已知运维痛点）。

**决策依据**：custom routing 不是"物理分片"与"逻辑过滤"两个选项之间的折中，而是同时拿到两边收益、不付两边代价——不需要为每个 space 预先分配独立资源（逻辑过滤方案想避免的运维负担），但检索精度和开销上等同于物理分片（物理分片方案想要的收益）。

这一收益对向量检索场景尤其关键，直接对应分 `space_id` 的核心设计动机之一——**控制单次向量检索的范围与开销**：

- Elasticsearch 的近似 kNN（HNSW）是**按分片独立建图**的。跨分片查询时，每个分片各自返回 top-k 候选，协调节点再做一次归并取全局 top-k——分片数越多、单分片数据越少，这个"近似的近似"引入的精度损耗越明显。
- 通过 `space_id` custom routing，同一 space 的向量数据落在同一分片，检索时只需在单个分片的 HNSW 图内做近似最近邻，完全不需要跨分片归并，精度与开销都等同于对该 space 单独建小索引检索。

**运维负载不均的应对**：一致性哈希只保证按 key 均匀分布，不保证按流量均衡——若某个 space 写入/查询量远超其他 space，其所在节点/分片物理负载会更重，这属于运维层面的应对（针对性扩容或权重调整），不改变分区键/routing 键的设计结论。若未来某个具体 space 确需硬隔离的 SLA（如企业级客户专属资源），可对该 space 单独做物理隔离（独立 keyspace/index），作为局部升级，不需要现在对所有 space 一刀切。

**已否决方案**：per-space 独立 Cassandra keyspace/集群；per-space 独立 Elasticsearch index。均因随 space 数量增长会带来持续的手动运维负担而排除，此决策同时影响 Cassandra 与 Elasticsearch 的分片/路由划分方式，两者保持一致的分片逻辑。

**v0.13 注记**：本节逻辑隔离定案**维持为当前阶段（自有小规模集群、体验与测试用途）的实施方案，继续有效**。但按 §0.5 价值观公理与服务商运维的商业模式，per-space 物理隔离已列为**目标架构方向**，上文"已否决"结论的适用范围限于当前阶段，不构成对目标架构的否定。**v0.16 更新**：目标架构已正式定案，具体形态为"存储物理隔离 + 计算共享 + 四层延迟/成本模型"（见 §15），切换前提为 §10 课题论证通过。

#### 7.5.2 消息/流转层选型（v0.7 定案）

**决策**：消息/流转层采用 **Apache Pulsar**，取代此前使用的 NATS JetStream。

**核心依据**：Pulsar 的 tenant/namespace 模型与项目"以 `space_id` 为单位分割"的整体架构原生契合——每个记忆空间可映射为一个独立 namespace，天然获得配额（存储配额、消息 TTL、限流）与策略隔离，且创建新 namespace 是轻量元数据操作，不需要像"每个 space 单独开一条 stream"那样预先分配专属资源。这一考量优先于组件学习成本——技术栈是否契合业务模型是团队认为无法靠工程投入弥补的因素，与此前放弃 Milvus（向量检索场景不契合）的判断依据一致。

**已比较并否决的方案**：
- **NATS JetStream**：功能上可满足持久化、consumer 独立进度、subject 级过滤等需求，但 subject 前缀只能做逻辑隔离，无法提供 namespace 级别的配额与资源策略，长期看与 space 隔离诉求的契合度不如 Pulsar
- **Kafka（自建/托管）**：吞吐能力对当前及可预见量级是过剩产能，且不具备 Pulsar 式的原生多租户 namespace 模型
- **Redis Streams**：持久化机制（AOF/RDB）不适合承担 §12 训练数据长期归档职责，排除
- **云厂商托管队列（Kinesis/SQS/Pub-Sub 等）**：retention 与 replay 能力不满足训练数据归档与多租户隔离需求，排除

**已知权衡（拍板时留痕）**：Pulsar 相比 NATS JetStream 多引入一层独立的元数据存储（ZooKeeper 或等效组件）及 BookKeeper 存储层，组件数与故障面均有增加；决策发生在验证阶段尚未产生真实吞吐/多租户隔离压力数据之前。团队判断架构契合度带来的长期收益优先于此，故直接定案，不再等待实测数据。

**沿用不变**：§7.5.1 Dead Man's Switch 机制原理不变，具体实现改为基于 Pulsar 的 consumer ack 与 backlog 监控（原文基于 NATS JetStream 的表述同步更新）。

#### 7.5.1 EX 摄入层的强制要求：Dead Man's Switch

**背景**：早期版本出现过"实时上传事件，某个时间点起悄悄不再上传"的故障，根因通常是失败被静默吞掉（客户端异常被 catch 未上报、鉴权 token 静默过期、背压导致队列丢弃、无主动监控）。

**决策**：EX 摄入层必须配置独立的心跳/dead man's switch 告警——若某个活跃记忆空间在设定时间窗口内完全没有新事件写入，主动触发告警，而非依赖"系统看起来在正常运行"这一假设。这是硬性要求，不是可选项。可直接基于 Pulsar 的 consumer ack 与 backlog 监控实现（v0.7 更新，原基于 NATS JetStream 的表述见 §7.5.2）。

## 8. 记忆空间模型（Memory Space）

**背景**：早期讨论曾用"Agent 记忆"作为顶层分区边界，但无法同时覆盖两类真实场景——(1) 同一项目内多个工具/Agent（如 Claude Code 负责规划、Codex 负责执行）协作时需要共享上下文；(2) 同一用户的多个项目之间需要严格隔离，避免污染。单一"Agent"维度无法同时满足"该共享的共享、该隔离的隔离"。

**决策**：顶层分区键改为更抽象的 **记忆空间（Memory Space，`space_id`）**，Agent/工具降级为空间内的"写入者身份"。

- **账号层级**：账号（IS）→ N 个记忆空间 → 每个空间内可有多个写入者（Agent/工具）身份
- **C 端场景**：一个记忆空间 = 一个 Kin（持续人格陪伴者）
- **开发者场景**：一个记忆空间 = 一个项目；Claude Code、Codex 等工具作为同一空间内的写入者，各自事件共享同一份 EX/RMS，通过 `agent_actor_id`（节点属性，非分区键）标注来源，保证协作上下文连续
- **多项目隔离**：不同记忆空间之间互不相通，天然解决"项目间相互污染"问题
- **RMS/EX 分区键**：从 `agent_id` 改为 `space_id`；`agent_actor_id` 降级为节点属性 `A_i` 的一个字段
- **`space_type` 枚举字段**：区分空间语义（如 `companion` / `project`），不影响 RMS/FS/SS 核心逻辑，仅作为上层产品/运营维度

**服务对象决策**：C 端（陪伴型 Kin）与开发者（项目型记忆空间）**两端都做**，架构层面成本低（仅需记忆空间抽象这一层，不需要为两端分别设计底层机制）。具体开放顺序/节奏根据实际情况另行决定，不在本文档中锁定。

**空间隔离是向量检索架构决策的直接依据**：§7.2 放弃 Milvus 的核心理由，正是建立在本节"检索永远限定单一 `space_id` 内、不存在跨空间检索"这一硬约束之上——这是架构不变量，不是阶段性判断，因此该决策对 2.0 同样成立，不存在"以后数据量大了要重新引入 Milvus"的情形。

## 9. MCP / SDK 接口设计（v1.0 定稿）

> **状态说明**：本节 v0.3 起为提案草稿，经 v0.10（`flag_conflict` 事件化）与 v1.0（§9.3 三项开放问题全部定案）修订后**定稿**。限流阈值、错误码等具体参数留待实施阶段标定。

### 9.1 背景与设计前提

MS 延期后，RMS→MS→外部 的缓冲层不存在，RMS 需要直接对外暴露接口。这里有一个容易混淆的点需要先厘清：**RMS 对外的"写入"，不等于 EX 的事件摄入**。

按现有架构（§7），原始内容应先落 EX（不可变 source of truth），再经 SS 打分、异步流入 RMS consolidation；这条路径不应被外部调用者绕过，否则 EX"唯一真相源"的定位会被破坏。但 §2.3 描述的 δ 动态更新中，+0.2 强化是对**已存在节点**的状态调整，不产生新内容，也不需要经过 SS 六维度重新打分——这类信号如果也走 EX→SS→RMS 全流程，会有不必要的延迟。−0.5 冲突失效则不同（v0.10 变更）：纠错在内容上必然伴随新信息（正确的内容是什么），本质就是新事件，因此走正常入链（见 §13.7），不再是直连 RMS 的旁路；下表中的 `memory.reinforce` 是唯一保留的直连旁路操作。

据此，接口按语义分为三类，而非简单的"读/写"二元：

| 操作 | 语义 | 底层行为 |
|---|---|---|
| `memory.record` | 写入新记忆 | 封装转发至 EX 摄入端点，不直接操作 RMS 图；对外行为看起来是写入，内部走完整 EX→SS→RMS 流程 |
| `memory.reinforce` | 强化已有记忆 | 直接修改目标节点 `φ_i`（`s += 0.2`、更新 `n_last_touched`、`reinforce_count += 1`），同步生效，不经过 consolidation worker |
| `memory.flag_conflict` | 提交纠错 | **v0.10 变更**：不再是直接改 RMS 的旁路操作——封装为携带被纠正事件引用的普通事件，转发至 EX 摄入端点走正常入链；consolidation 阶段据此建立 supersedes 边并对旧节点异步施加 −0.5（见 §13.7）。纠错是低频、非延迟敏感操作，异步代价可接受 |
| `memory.retrieve` | 检索 | §5 四阶段检索流程的外部入口，只读 |

### 9.2 鉴权设计

沿用 §7 已定的 OAuth/JWT 方向。关键决策点：**`agent_actor_id` 不由请求体声明，而是从凭证本身解出**。

- IS 为每个写入者身份单独签发凭证
- JWT claim 结构：`account_id / space_id[] / agent_actor_id / scope`
- `scope` 取值对应 §9.1 四类操作：`record | reinforce | flag_conflict | retrieve`
- 若同一 `space_id` 下的多个写入者身份（如 Claude Code、Codex）共享凭证并允许客户端自行声明 `agent_actor_id`，会破坏 §8 强调的"协作可追溯性"——因此该字段必须绑定凭证，不接受请求体覆盖

### 9.3 原开放问题（已全部定案）

以下三项原为本节优先级最高的开放问题，现已全部定案：

1. ~~**`memory.flag_conflict` 滥用防护**~~ —— **v0.10 已消解**：纠错改为事件化入链后（§13.7），−0.5 不再由调用方直接施加，"反复标记冲突误杀记忆"的攻击面随之消失；滥用等价于向 EX 灌垃圾纠错事件，由摄入层统一限流/鉴权处理，不再是本接口的独立问题。supersedes 边的建立由 consolidation 负责，同一对节点重复建立为幂等操作
2. ~~**`memory.retrieve` 返回结果是否暴露内部 FF 字段**~~ —— **v1.0 定案**：默认**不暴露**（返回内容+关系的干净结果，避免内部状态泄露使 FF 机制成为可操纵对象）；带 `debug` scope 的凭证可在 retrieve 时要求附带 φ_i 内部字段（`s_effective`、`n_star_cached`、计数器等），供开发者/项目型空间调试"某条记忆为何被/未被检索"。**开关绑定 JWT scope 而非请求参数**——与 §9.2 `agent_actor_id` 绑凭证同一设计逻辑：权限类开关不信客户端自报；C 端产品凭证不授予 `debug` scope
3. ~~**`memory.record` 的返回时机**~~ —— **v1.0 定案**：**同步等待 EX 落库确认后返回**。调用方获得"写入成功"的即时反馈，与 §7.5.1 Dead Man's Switch 哲学一致（不依赖"看起来写入成功了"的假设）；EX 落库后流向 SS→RMS 的后续处理仍为异步，不在返回路径上

## 11. 运维模型（提案）

> **状态说明**：本节覆盖 JanusGraph+Cassandra+Elasticsearch 技术栈落地后的运维组织方式。核心结论：靠谱的运维不取决于"人还是 AI"，而取决于是否提前建好边界触发点、升级规则与可观测性基础设施——这些基础设施缺失时，人类同样需要逐层排查，效率优势会被系统不透明性抵消。

### 11.1 人机协作分工

- **PM Agent（强模型）**：承担日常巡检、报表生成、已知模式的异常检测与告警、按 runbook 执行的标准化操作（重启、扩容、索引重建等），并对未知/复杂故障做初步排查、给出诊断与处理建议
- **真人运维（决策岗，三班倒覆盖）**：对 Agent 升级上来的问题做最终判断和拍板，尤其是高风险操作（详见 §11.2）；一个"决策岗"在 7×24 覆盖口径下按行业惯例对应 3-5 人（三班倒最低配 3 人 + 覆盖休假/病假的富余量），需在人力预算中明确这一折算系数

**分工依据**：PM Agent 在训练数据覆盖的公开知识、已知故障模式上的广度大概率超过小规模团队的个体经验总和；但涉及"当下这套系统的实时状态诊断""高风险决策的止损判断""前所未见的新型故障根因定位"，目前没有生产实践证据表明 Agent 判断力已稳定超过资深工程师，这部分应保留人类决策权，尤其是涉及 EX（不可变 source of truth）等不允许出错的组件。

### 11.2 升级触发边界（"必须升级"清单，需团队定稿细化）

- 任何触及 EX 写入路径的操作
- 任何影响范围跨越多个 `space_id` 的操作
- 任何此前从未出现过的错误模式
- 任何 Agent 自身置信度低于设定阈值的判断

该清单不是一次性产出，应随运维案例积累持续细化。同时需为"真人决策岗暂时无法响应"设计降级预案——原则上只做防止损失扩大的保守操作，不做任何不可逆操作，等待人工介入。

### 11.3 决策留痕机制

Agent 给出的诊断/建议、真人的最终决策、实际执行内容、处理结果，应完整记录。用途有二：一是审计需要；二是这批"Agent 建议 vs 人类最终决策"的对比数据，是后续校准 Agent 置信度阈值、判断哪类问题的 Agent 建议已经足够可靠、可适度放宽升级门槛的核心依据。

### 11.4 1.0 阶段主动压力测试与决策留痕提前启动（v0.5 新增）

**背景与决策**：JanusGraph+Cassandra+Elasticsearch 技术栈选择在 1.0（尤其前 100 名种子用户阶段）单节点部署落地，核心理由并非单纯的成本/复杂度权衡，而是**风险容忍度的时间窗口错配**——1.0 种子用户阶段即便发生全线崩溃、数据丢失，业务代价可控；2.0 用户增长期一旦发生同级别事故，代价会指数级放大。因此 1.0 阶段应被有意识地当作技术栈与运维团队（含 PM Agent）的磨合期，而非单纯的"跑起来看看"。

**要求一：主动制造故障场景，不能只依赖自然发生的故障**。低负载的种子用户期，系统大概率不会自然触发"Cassandra 节点抖动级联到 JanusGraph 遍历超时"这类级联故障。1.0 阶段应规划一轮**混沌工程测试**（chaos engineering），有计划地模拟节点宕机、网络分区、磁盘满、Elasticsearch 索引损坏等场景，主动触发团队与 PM Agent 需要磨合的故障模式，具体场景清单与演练节奏见 §10 待决问题。

**要求二：§11.3 决策留痕机制从 1.0 第一天启动，不等到 2.0 前补**。只有从种子用户阶段起持续积累"Agent 建议 vs 人类最终决策"的真实记录，到 2.0 上线前才有可验证的依据判断"团队与系统是否已磨合成熟"，而非仅凭"跑了几个月没出大事"的模糊判断。

### 11.5 多租户工程红线（v0.12 新增）

沉淀自对"数十亿 Space + per-space 全物理隔离"外部架构方案的评估（评估结论见版本记录，原文存档备查）。以下红线与隔离方案选型无关，无论逻辑隔离还是未来局部物理隔离均成立：

- **红线 1：禁止全局广播 / 跨 space 全集群扫描**。运维后台、批处理、数据分析任务的入口必须绑定显式 space 列表，不存在"扫一遍所有空间"的合法操作形态；这同时是 §8 空间隔离架构不变量在运维侧的对应
- **红线 2：单 space 资源配额**。顶点/边数量上限、ES 侧单 space 存储与向量条数上限、单次图遍历最大跳数与返回节点数上限。逻辑隔离下这条比物理隔离场景更关键——单个 space 无限膨胀会拖累共享集群上的所有租户
- **红线 3：冷热分层**。数十亿 space 量级下必然出现极强冷热分化：热 space 保障资源；冷 space 降低后台 sweep 频率（§13.3）、Redis 缓存优先逐出。注意约束：共享 index + custom routing 方案下，ES 层面无法对单 space 做索引级冻结，存储层冷热控制主要依赖 §13.4 归档机制；未来升级为独立 index 的企业级 space（§7.4 逃生门）可获得完整的存储层冷热分层能力

## 13. 记忆维护机制与 FS 落地（v1.0 定稿）

> **状态说明**：本节 v0.9 新增提案，补齐此前版本的空白——FF 公式（§2）与 φ_i 字段（§4.1）定义了"记忆状态是什么"，但未定义"谁在何时执行维护"；FS 在 §1 之后全文再无落地设计。经 v0.10（纠错机制）、v0.11（reinforce 重建性）、v1.0（§13.4 删除权粒度定案）修订后**定稿**。参数取值（N_neglect、宽限期、固化阈值等）留待实测标定。

### 13.1 衰减不物化：存储层只保存基准显著性

**决策**：FF 的指数衰减部分**永不写回存储**。存储中的 `s` 仅记录经 δ 调整（+0.2 / −0.5 / −0.1）后的**基准显著性**；`s_effective = s × e^(−λ·Δn·log(1+t/t₀))`（Δn = n_now − n_last_touched）一律在读取时现算。

**依据**：
1. §5 查询流程本来就是现算 `s_effective` 的，物化衰减只会引入"存储值 vs 现算值"的双写不一致风险
2. 衰减是纯函数（给定 s、n_last_touched、n_now，结果唯一），没有任何信息需要通过写回保存
3. 避免后台任务的全图写放大——事件距离每推进一步，所有节点的 `s_effective` 理论上都在变，物化等于按事件频率持续重写全图

§4.1 φ_i 中 `s` 的语义相应修正为"基准显著性"（原"实时值"表述作废）。

### 13.2 事件序号 n：space 级单调计数，EX 摄入路径分配

- **按 `space_id` 独立计数**：与 §8 空间隔离原则一致，跨空间不存在共享的事件距离语义
- **分配点**：EX 摄入路径。事件写入 EX 时获得该空间的下一个序号，作为事件的不可变属性；RMS 节点创建时继承为 `n_created`
- **n_now 读取**：各 space 当前序号缓存于 Redis（§7.5 已有组件），由摄入路径维护；缓存失效时从 EX 查询该 space 最新事件序号重建
- **事件类型分层（v0.11 新增）**：EX 事件分为**经验事件**与**元事件**两类，只有经验事件推进 n。reinforce 记录（§13.7）等元事件只留痕、不消耗事件序号——否则检索越活跃、强化越多，n 推进越快，所有记忆衰减越快，"用得越多忘得越快"，背离 FF 语义
- **`n_last_touched` 更新时机**：仅在 +0.2 强化（`memory.reinforce` 同步生效）与 −0.5 冲突失效（consolidation 异步施加，§13.7）时更新；忽视惩罚不更新（§13.3，否则惩罚自我抵消）

### 13.3 忽视惩罚（−0.1）：FS 周期扫描，按区间幂等触发

**决策**：−0.1 天然没有外部调用方（"长期未被触及"不是一个事件），由 FS 的后台 sweep worker 周期执行。

- **触发条件**：节点满足 `n_now − n_last_touched ≥ (neglect_count + 1) × N_neglect` 时，`s -= 0.1`，`neglect_count += 1`；**不更新 `n_last_touched`**（否则惩罚会自我抵消）
- **N_neglect**：agent-level constant（归入 §2.2 参数分层），与 λ 同层按域固定
- **φ_i 新增字段 `neglect_count`**：与 reinforce_count/conflict_count 同用途——审计，以及幂等保证（每个忽视区间至多触发一次，sweep 重跑/重复扫描不会产生重复惩罚）
- **扫描节奏**：sweep 按 space 分批执行，节奏只需显著快于 N_neglect 对应的事件推进速度，不追求实时；sweep 任务本身的存活性参照 §7.5.1 Dead Man's Switch 思路纳入监控（sweep 停摆等于忽视惩罚静默失效，与"事件悄悄不再上传"是同构故障）

### 13.4 节点生命周期：活跃 → 归档 / 固化，物理删除为例外

跌破 θ_effective 的节点**不从图中删除**（§4.3 已定检索时跳过即可，边随之自然失效），生命周期三种去向：

| 去向 | 触发条件 | 语义 |
|---|---|---|
| 归档（archive） | `s_effective` 跌破 θ 且按 `n_star_cached` 预测已跨越遗忘视界、再经过宽限期，期间无任何 δ 触发 | 从 JanusGraph 热图移除，归档副本（节点字段 + 图邻接快照）写入冷存储；EX 原始记录不受影响，`ref_ex` 保证可溯源重建 |
| 固化（consolidate） | `reinforce_count` 达阈值且期间无 conflict（沿用 §6.1 存档草案的判定思路），或显式调用 | 节点标记为固化：`s` 锁定、跳过衰减计算与 sweep，检索时不再被 θ_effective 过滤 |
| 物理删除 | 仅用户主动请求（隐私/删除权场景） | 见下方 v1.0 定案 |

**物理删除（v1.0 定案）**：删除权以 **space 为最小单位**——支持**整 space 物理销毁**（用户注销一个 Kin、删除一个项目）：清除该 space 的 EX 事件流、RMS 图存储与索引、Pulsar namespace、Redis 缓存，全流程校验无残留。整 space 销毁与 EX 不可变性不冲突：不可变性防的是**运行期篡改**，整空间销毁是**用户行使删除权**——且按 §14，任何删除方案不得影响其他 space 的数据完整性。**空间内单条事件的物理删除不支持**：从只追加日志中抠除单条会破坏事件序号 n 的连续性语义（§13.2）与 RMS 可重放重建性（§13.7）；空间内的"删除"诉求由纠错机制（§13.7，supersedes + 软减分）与归档承接。目标架构（§15）下整 space 销毁更简洁：DROP keyspace + 删除独立 index + 删 namespace + 清缓存，影响范围物理收束在该 space 内。

### 13.5 FS 职责清单（落地）

- **周期 sweep**：忽视惩罚执行（§13.3）、归档判定与执行（§13.4）
- **`n_star_cached` 刷新**（细化 §4.4 的"顺带刷新"为两条具体规则）：节点发生任何 δ 调整时立即重算；sweep 过程中顺带刷新临近遗忘视界的节点
- **固化判定与执行**（§13.4）
- **职责边界**：FS 不做图拓扑推断（实体/因果边推断仍归 §4.4 consolidation worker）；不持有 λ、N_neglect 之外的任何检索参数（ρ、θ_base 为查询时参数，见 §2.2/§5）

### 13.6 与既有章节的一致性修订

- §4.1 φ_i `s` 语义修正为"基准显著性"（见 §13.1），φ_i 新增 `neglect_count` 字段（见 §13.3）
- §12.2 原引用"§7 RMS 存储节点归档/物理清除机制"为悬空引用（§7 并无该机制），实际指向本节 §13.4，已修正

### 13.7 纠错机制：supersedes 关系与事件化纠错（v0.10 定案）

**决策**：纠错**不是**对旧节点的状态操作，而是一条携带被纠正引用的**普通 EX 事件**。取代关系由因果图中的 `supersedes` 边表达（§4.2），**不设硬失效标志**。

**设计原则：数据层只存事实，判断下沉到查询时策略。**
- 硬失效标志（tombstone/invalidated）是把"这条是错的"这一**判断**烧进数据：不可撤销、无法表达"纠错本身改错了"，与 EX 不可变哲学冲突，已否决
- supersedes 边记录的是"n_old 在 τ 时刻被 n_new 取代"这一**事实**；"被取代节点是否返回、如何降权"是 §5 检索策略的事，策略演进不需要回写历史
- −0.5 冲突失效**保留为软减分**：它服务的是 FF 衰减动力学（让被取代节点淡得更快），不是对错判断，与 supersedes 边各司其职

**流程**：
1. 调用方经 `memory.flag_conflict`（§9.1）提交纠错事件，事件体携带被纠正事件/节点的引用
2. 事件走完整 EX→SS→RMS 入链，在 EX 留下不可变记录——**supersedes 关系从此可从 EX 重放推导**，冲突路径不再有重建性缺口
3. consolidation worker 建立 `n_new --supersedes--> n_old` 边，对旧节点异步施加 −0.5、`conflict_count += 1`（同一对节点重复纠错幂等）
4. 检索侧按 §5 supersedes 处理规则执行：默认重定向至取代者，被取代节点不进候选池（显式追溯历史除外）
5. 纠错可链式嵌套（A→B→C），沿链取最新有效节点；任何一环的判断变更都只是查询策略变更

**reinforce 的 EX 重建性（v0.11 定案）**：+0.2 reinforce 保留直连 RMS 的同步旁路（检索命中需立即强化，延迟敏感），**同时异步追加轻量元事件到 EX**（fire-and-forget，调用方不等确认），换取 RMS 从 EX 的完整可重建性。两条约束：

1. **元事件不计 n**：reinforce 记录是元事件，按 §13.2 事件类型分层只留痕、不推进事件距离
2. **时间窗合并**：reinforce 是高频信号，同一节点在短时间窗内的多次强化合并为一笔追加（附 count），控制 EX 写放大；重建精度降至窗口粒度，对 reinforce 语义可接受（区别于纠错——纠错每笔必须精确，故走完整入链不合并）

至此 RMS 全部状态（图结构、δ 调整历史、supersedes 关系）均可从 EX 重放重建——这对事故恢复、§11.4 混沌演练中的"删了重建"场景、以及未来迁移都是架构级保障。§10 对应待决项勾除。

## 14. 记忆可携带性与迁移（架构不变量）

> **地位说明**：本节是**使命级约束**，优先级高于任何具体技术选型。记忆是用户的核心资产，Lethefield 作为记忆服务，任何架构决策与技术演进都不得损害用户对其记忆的完整所有权、可导出性与可迁移性。后续所有版本的技术定案，凡与本节冲突者，需回到本节重新评审。

- **完整导出权**：以 space 为最小单位，用户可随时导出其全部记忆——EX 原始事件流（含 reinforce 等元事件）、RMS 图快照（节点、四类边、supersedes 关系、φ_i 状态）。导出格式必须是开放标准格式，非私有二进制，保证脱离 Lethefield 后仍可解析、可重建
- **可重建性是便携性的地基**：§13.7 已保证 RMS 全部状态可从 EX 重放重建——**导出 EX 即等价于导出全部记忆状态**，这是该定案在"事故恢复"之外的第二重价值；导出管线的实现复杂度因此大幅降低
- **迁移自由度**：space 是最小迁移单位，支持整 space 在集群间、部署形态间迁移（云端 → 未来本地/混合部署，见 §0 部署策略）。逻辑隔离方案（§7.4）天然支持这一点——单 space 数据在 Cassandra 按分区键聚拢、在 ES 按 routing 聚拢、在 Pulsar 按 namespace 聚拢，抽取边界清晰；未来对特定 space 升级物理隔离（§7.4 逃生门）后同样成立，且更彻底
- **与删除权的关系**：可携带与可删除是所有权的一体两面；删除权粒度 **v1.0 已定案**——整 space 物理销毁（§13.4），空间内单条删除不支持；任何删除方案不得影响其他 space 的数据完整性
- **对供应商锁定的明示立场**：不通过私有格式、不可导出的内部状态、或人为迁移成本制造用户黏性。用户留存应来自服务质量，而非离开难度

## 15. 目标架构：per-space 物理隔离（v0.16 定案）

> **状态说明**：本节为**目标架构**定案，不影响当前阶段实施——§7.4 逻辑隔离继续作为现阶段（自有小规模集群）方案执行，切换前提见 §15.4。推导链：§0.5 公理 3（威胁不可来自开发者，需结构性保证）→ v0.13 确立物理隔离为目标方向 → v0.15 澄清边界（运维方信任模型为法律+市场，per-space 加密非公理要求）→ 本节定案具体形态与成本边界。

### 15.1 定案范围：存储物理隔离 + 计算共享

- **存储物理隔离**：每个 space 独立 Cassandra keyspace + 独立 Elasticsearch index。数据层获得**结构性保证**：任何代码 bug（如漏带过滤条件）在架构上不可能造成跨 space 读写——不满足公理 3 的"程序性保证"，而是其要求的"结构性保证"
- **计算共享（对全量计算隔离的明确让步）**：JanusGraph 共享计算池 + LRU 图实例缓存，不追求 per-space 常驻实例。共享计算意味着查询路径上不同 space 跑在同一批 JVM 内，越界防护在计算层依赖连接级隔离而非实例隔离——**数据层的结构性保证完整成立，计算层不追求物理隔离**。这是用计算层的让步换取两个数量级的成本下降（见 §15.3 已否决项）
- **per-space 加密**：非公理要求（§0.5.2 运维方信任模型），作为服务商差异化竞争的可选产品特性，不进核心架构

### 15.2 四层延迟 / 成本模型

| 层 | 定义 | 访问延迟 | 单 space 月成本（量级估算） |
|---|---|---|---|
| **热** | 图实例在 LRU 缓存中 | 毫秒级 | 含于下项 |
| **温/冷（主体）** | 存储常驻（keyspace/index 留在集群），图实例按需 open | 首开秒级（graph open），随后进缓存变毫秒级 | **约 0.05~0.5 美元**（ES 分片堆开销为主要约束，冷 space 降配 1 主 0 副本） |
| **封存** | 超长期零访问（阈值待定，如 1 年），快照至对象存储，从集群移除 | 分钟级恢复 | **<0.01 美元** |
| **Premium** | per-space 全常驻实例（计算+存储），企业付费档 | 毫秒级 | **3~10 美元** |

设计要点：普通冷 space **永远不走快照恢复**——分钟级恢复只存在于封存层；"存储常驻 + 计算共享缓存"使绝大部分 space 的最坏延迟为秒级首开，用户体感等同打开久未使用的应用。

### 15.3 成本边界

- **固定税只按存储常驻支付**（约 0.05~0.5 美元/space/月）；计算池按并发 QPS 扩容，与 space 总数无关
- **单集群容量约束**：Cassandra 约 1000~2000 space/集群（keyspace 元数据与 memtable 上限）；ES 分片堆开销为更紧约束（降配后数千 space/集群）。超过容量需集群池 + 租户调度器（§10 课题 2）
- **成本边界线**：温冷层 0.05~0.5 美元/space/月是商业模式必须能覆盖的下限——授权/服务费定价需与此对齐（信托侧商业题，架构侧提供此数字）

**已否决方案**：
- per-space 计算全常驻：每 space 一个常驻 JVM（≥0.5GB 堆），3~10 美元/space/月纯闲置内存费，10 万 space 即 30 万~100 万美元/月，仅作为 Premium 付费档保留
- 默认冷快照（所有冷 space 踢出集群）：分钟级恢复延迟用户不可接受，快照仅限封存层

### 15.4 阶段路线

- **阶段 0（现在）**：逻辑隔离（§7.4），自有小规模集群，功能与运维磨合（§11.4）
- **阶段 1**：存储物理隔离落地——per-space keyspace/index、集群池 + 租户调度器、共享计算池 + LRU 图缓存。切换前提：§10 课题 (1)(2) 论证通过
- **阶段 2**：分层体系完整化（封存层阈值与自动化、Premium 档）、第三方服务商部署运维规范（§10 课题 3）

**与既有决策的一致性**：空间隔离架构不变量（§8）、检索限定单 space（§7.4）、§11.5 工程红线（配额、禁止跨 space 扫描、冷热分层）在目标架构下全部继续成立且更彻底；§13 记忆维护机制与隔离形态无关，不受影响；§14 可携带性在物理隔离下更简洁（整 keyspace/index 导出即整 space）。
